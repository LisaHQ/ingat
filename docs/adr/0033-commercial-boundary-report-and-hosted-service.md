# ADR-0033 Commercial boundary, outbound status report, support bundle and the hosted service

**Status:** Accepted (owner, 2026-10-19). Supersedes the notification sentence of [ADR-0022](0022-delegated-concerns.md) (now superseded in part): notification may also go to a receiver the owner enrolled, through an outbound report the host scheduler sends. Narrows the non-goals "a notification channel" and "a web UI, daemon, agent" in [ARCHITECTURE.md](../ARCHITECTURE.md) §1.4 to the host side.

## Context

Ingat is complete and limit-free under Apache-2.0, but nothing tells an owner how their hosts are doing except the scheduler's failure mail, and the owner wants a free tier and a paid tier without weakening the floors F1-F17, the approval classes or the generality rule, and without a listener, a daemon or a third-party dependency in the tool. Three models were judged: a hosted hub holding customers' bundles, an offline licence file with limits in the CLI, and a free tool with paid work plus a hosted status page. The third won on every criterion that touches the floors.

The owner then asked what survives a world where writing code and recipes is cheap because of AI agents. The answer shaped the priorities below: what AI makes cheap (writing a recipe, a backup script, a support answer) is not the product; what it does not replace is evidence (a backup proven restorable by an independent, pinned, tested system), a safety harness for agents that operate hosts, and a running service with someone accountable.

## Decision

**Commercial boundary (verbatim rule).** *Nothing that preserves or recovers data is ever paid, limited or tier-dependent.* The tool has no plan, licence, key, feature flag, instance limit or download path from any service. The tool is positioned as the safety harness for apps on one host, built so that AI operations agents can use it without being able to lose data: the plan and hash hand-over of [ADR-0013](0013-approval-classes-and-plan-files.md) (M2), and later a read-only agent interface with plan hand-over, by its own ADR. A `TRADEMARKS.md` reserves the name for the hosted service; a `docs/LICENSING.md` says in everyday words what is free (everything in the tool, forever) and what is sold. A fork may use the tool freely and must rename a hosted service.

**Priorities (owner, 2026-10-19), in order:**

1. **The tool stays free and whole**, with the agent-facing features above. Nothing in `src/` knows a tier, a licence, a quota or a network endpoint beyond the outbound report below.
2. **The hosted service is the paid product.** A status page the owner operates: a free tier with limits (hosts, instances, history, one dead-man email when a host stops reporting) and a paid tier per host (longer history, alerts on new attention, an old backup or test restore, low disk, quiet hours). Later, each by its own ADR: off-site encrypted copies (host-held keys, parts with per-part hashes, recovery only through `import`, never before M4), and approval of an agent's plan from a phone (the host asks outbound; nothing inbound; class D never). The service is a separate private repository, deployed by Ingat on the owner's own host, which also yields the generic Linux certification of [ROADMAP.md](../ROADMAP.md) M4 slice 12.
3. **The catalog is free or cheap.** Community members and agents write entries ([ADR-0031](0031-data-providers.md)); the value the owner keeps is the certification pipeline that proves each entry restores. Paid onboarding, where it exists, is priced low and treated as a way to grow the catalog, not as income.
4. **Support and host certification** stay minor paid services: evidence review (the platform part of `facts.json` and a `selftest --host` log, reviewed and committed within an agreed time), priority answers; no host access, no SLA until a second responder exists.

**Tool change 1: the `report` command group.**
- `report enroll` (class C, host lock, the host name typed on a terminal, `Cmd("C", "host", "typed", False, True)`, beside `host init` in LIFECYCLE §2): reads a one-time enrolment code from stdin (valid 15 minutes; never argv), exchanges it for a token over HTTPS, writes `host/report.toml` (`url`, `host_label`, `interval_minutes`) and `host/report.token`, both `0600`. `report disable` (class C, the same approval) removes both. Enrolment is the owner's act, never an agent's: an operations agent (class A and B, OD-10) cannot enrol a host. `host init` never creates these files: reporting is off until the owner enrols.
- `report preview` (class A, writes nothing): prints the exact payload that would leave the host.
- `scheduled report` (class B, unattended, runs in the CLI container without an executor; writes only `host/report.json` and `host/report.cursor.json`): one `POST {url}/v1/hosts/{host_id}/reports` with a bearer token and an idempotency key, body at most 64 KiB, timeout 10 s, no retry. `host_id` is the first 16 hex characters of SHA-256 over the engine ID plus a salt kept in the token file. Payload schema 1 (the outbound report's own schema, unrelated to the `output_schema` of the CLI's `--json` answers in ADR-0032): tool version, gate tier, the platform build keys that `support/hosts` files already allow, free-space percentages per root, and per instance: name, app id, deployment seq, state, attention codes, ages in hours of the last bundle, `verified` and `restore-tested`, the open operation's kind and step state, plus, for the `host/runs` records newer than the cursor, the typed fields only: `run_id`, `exit`, `code`, `op` and the record time, never `message` or `next`. Never: ports, URLs, hostnames, paths, params, app env values, secret names, bundle hashes, captured text. A payload-shape test fails when any other key of a run record reaches `report preview`.
- The receiver's answer is mapped to a closed code set (`accepted` with the next interval, `limit`, `retry`, `revoked`, `bad-answer`) and only the tool's own word-table text for that code is ever shown; the raw body, bounded to 1 KiB, is stored in `host/report.json` under a key no renderer prints. Nothing from the receiver is executed, and nothing from it is shown as advice: `next` and every attention line come from the tool. The scheduler runs the job at its own cadence; the job sends only when `interval_minutes` has elapsed since the last accepted report, and the receiver's next interval is advisory and can only lengthen that wait. Exit 0, except exit 5 once when the outcome changed since the last run (the `scheduled status` dedupe rule). `doctor` shows when the last report was accepted; a new attention code `no-offsite-copy` is computed on the host from facts the owner records, never from the service.
- The outbound client lives in its own module `adapters/http_out.py` (`post_json`): HTTPS only (`report enroll` refuses any other scheme), certificate verification against the system store, an opener without a redirect handler (any 3xx is `bad-answer`, so the token never follows a redirect), no proxy handler, 10 s timeout, body and answer bounded. The secret canary gains a case with a redirecting receiver that never sees the token.

**Tool change 2: `support-bundle <i>` (class A).** Streams a tar to stdout: the instance's records, `ops/*/steps.jsonl` and `progress.log`, `host/certifications/*`, the `host/runs` records of that instance, `doctor` and `status --json` output, and typed `docker version` and `docker info` fields, all through the instance's redaction set. Always excluded: `secrets/`, deploy keys, bundles; `instance.toml` only with `--include-config` and without secret keys. The file reaches anyone only when the owner attaches it by hand; the service never receives it.

**Modules.** `model/report_config.py`, `ops/report.py`, `ops/support_bundle.py`, `adapters/http_out.py`, `cli/commands_report.py` (the `report` and `support-bundle` parsers, help and handlers, registered from `parser()` so `cli/commands.py` does not grow), `ops/doctor.py` (the last-report line and `no-offsite-copy`; the split of [ADR-0032](0032-local-session-bound-web-view.md), done by whichever of R0 and U1 lands first) and `model/words.py` (a title and a what-to-do line per attention code and per receiver code). No new dependency: `urllib.request`, `ssl`, `tarfile`, `hashlib`, `json`. The default receiver URL lives in `brand.py`. Every string a person reads in the new commands, the catalog READMEs, the pages and the alerts follows the plain-language rule.

## Alternatives

- **A hosted hub holding customers' bundles** (rejected for now): the highest burden and liability for one owner, reverses two non-goals, holds the instance lock during uploads, cannot ship before M4 `import`, and adds nothing to app coverage. Its enrolment flow, push intake and dead-man email are adopted; its off-site copies are the post-M4 candidate above.
- **An offline signed licence with limits in the CLI** (rejected): not a service, it gates the unattended test restore and `apply` inside a safety tool so free users are less safe, is trivially bypassed in a public codebase, mislabels a refusal exit code, and composes with neither a web view nor a catalog. Its no-host-clock discipline, refusal house style and merchant-of-record advice are adopted; owner-signed certifications and CLI instance limits are not.
- **Paid onboarding and support as the main income** (the judged winner's original emphasis; demoted by the owner on 2026-10-19): time-for-money that AI agents make cheap; kept only as minor services.

## Consequences

Floors untouched: the new commands open no operation, take no effect token and touch Docker read-only. F2/F9: `report preview` and `support-bundle` join the no-trace suite; `scheduled report` writes only `host/report.json` and `host/report.cursor.json`, listed beside `host/attention.json`. F3: enrolment needs the owner's typed approval; the receiver can neither approve nor name a next step. F10: the service displays ages; only the tool writes `verified`. F12: the payload and the tar bytes join the secret canary suite; the token is read by path only and never follows a redirect. F14: the gate reads `tested.json` and certifications only; the receiver's answer is never a gate input. F17: no new switch. Approval classes unchanged; the owner as support never answers a class D challenge for a customer.

Design documents changed with this ADR: ARCHITECTURE §1.4 and §4.1 (a Planned note), LIFECYCLE §2 (the `report` and `support-bundle` rows) and §7 (the `scheduled report` entry), ROADMAP §4 and §5, ADR-0022's status, README; a `docs/REPORT_PROTOCOL.md` documents the endpoint and a small standard-library receiver when slice R0 lands, so the report can go to a receiver the owner hosts. Revenue expectations are modest: a solo-maintained tool with a small service, not a company; the tool's first value remains the owner's own apps running safely. Prices and limits are set outside this repository. Week estimates in [ROADMAP.md](../ROADMAP.md) §5.
