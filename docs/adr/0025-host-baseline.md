# ADR-0025 Host support tiers and the first platform profile (Synology DSM 7.4)

**Status:** Accepted (owner, 2026-10-14); revised the same day, before any implementation, by the owner's clarification that Ingat targets any host that runs Docker and Docker Compose. The earlier title was "Synology host baseline (DSM 7.4, Container Manager 24.0.2)".

## Context

Ingat is meant for any device or environment that runs apps with Docker and Docker Compose: bare-metal servers, VMs, VPS, NAS appliances that offer Docker (Synology or any other vendor) and small boards. Synology DSM is only the first real deployment. The package first assumed an unknown DSM host, possibly arm64 or low-RAM, possibly Btrfs. A read-only probe of the first host and platform research give the traits of DSM 7.4.1 with Container Manager 24.0.2-1706: Synology's build of Engine 24.0.2 (API 1.43), containerd 1.7.1 and runc 1.1.7; a vendor kernel, 4.4.x on many DSM 7.x platforms (some newer platforms run 5.10); cgroup v1; no CPU CFS quota/period; no blkio throttle; AppArmor without seccomp; default logging driver `db`; live restore off; a storage driver that depends on the volume filesystem (aufs on ext4 volumes, btrfs on Btrfs volumes); Snapshot Replication only on Btrfs volumes; the host's own Compose plugin v2.20.1 and Python 3.8/3.9; Docker access only as root; DSM Task Scheduler as the scheduler; and Container Manager project actions that delete data. DSM 7.1 and earlier ship the legacy Docker package (Engine 20.10, API 1.41, Compose v1), and DSM 7.1 is out of extended life. Upstream dind in CI reproduces an upstream Engine on Linux, never a vendor build. GitHub-hosted arm64 runners are free for public repositories (to verify in M0).

## Decision

- **Scope.** Ingat runs on one host with a local Linux Docker Engine 24.0 or later (API ≥ 1.43) and Compose v2, on any distribution or appliance, with the minimum host requirements of [ARCHITECTURE.md](../ARCHITECTURE.md) §11.4. Platform differences (CPU CFS quota, cgroup version, logging driver, storage driver, kernel, architecture, live restore, seccomp) are detected capabilities, and each platform build is certified on its own; no code path branches on a platform name, vendor or model (the generality rule, [ARCHITECTURE.md](../ARCHITECTURE.md) §11.3). A platform profile is documentation and certification data, never a code path.
- **Support tier 1:** Linux hosts running upstream Docker Engine (docker-ce or distribution packages) on an Engine line that CI tests (the dind lanes). A local `selftest --host` certifies each platform build for gate tier 2 ([ADR-0014](0014-tiered-version-gate.md)). The first committed generic Linux certification (VPS or server) is part of M4.
- **Support tier 2:** vendor-built engines on appliances, which need a platform profile: the full certification checklist and a committed certification for each platform build line, plus a local `selftest --host` after every update. Synology Container Manager is the first; other vendors follow, each with its own profile.
- **Not supported in v1:** rootless Docker, Docker Desktop on Windows or macOS for production use (development only), Podman, Kubernetes or Swarm, multi-host, Docker Engine older than 24.0 (API below 1.43). The last excludes Synology DSM 7.1 and earlier with the legacy Docker package: no tier, CI lane or certification. Support claims name only tested combinations.
- **Architecture.** One multi-arch image (`linux/amd64` and `linux/arm64`) from M1; an arm64 CI lane on GitHub-hosted arm64 runners runs the 29.x dind tag, and arm64 is claimed only for the combinations that lane passes. The first deployment is amd64.
- **Defaults.** Generic default roots `/srv/ingat` and `/srv/ingat-backups`, configurable at install; a platform profile passes its own (DSM: `/volume1/ingat` and the `/volume1/ingat-backups` shared folder). Off-host copies use the platform's tools (Hyper Backup on DSM; restic, borg or rsync on Linux). `schedule render` supports systemd timers, cron as a fallback and DSM Task Scheduler (M3).
- **First platform profile: Synology DSM 7.4 with Container Manager 24.0.2 on x86_64** (support tier 2). Each combination of DSM version (update level included), Engine build (as `docker version` reports it), kernel, storage driver and architecture is certified on its own, and the certification file also records the Container Manager build; after any update, `selftest --host` re-certifies the new build before gate tier 2 runs again, and the full checklist runs only for a new DSM minor line or a Container Manager build that changes the Engine, containerd or runc.
- The override gives every service without its own `logging` the `local` driver with rotation, and the executor uses it too; the CLI container and terminal tasks log to the `none` driver, so a terminal secret is never written by a logging driver, whatever the platform's default driver (safety floor F12, [LIFECYCLE.md](../LIFECYCLE.md) §1).
- The plan-time capability check refuses non-zero `cpus` limits on hosts without CPU CFS quota support (observed on DSM 7.4.1 with Container Manager 24.0.2-1706); consumer instances there set their `cpus` params to `"0"`, and an app change that makes "no limit" its default is required only if spike S11 shows that `"0"` is not "no limit". Docker silently discards unsupported blkio limits with a warning, so there is no blkio check until an app needs I/O limits (by ADR).
- A runc older than 1.1.12 is recorded by host certification as a CVE-2024-21626 exposure; on the DSM profile (runc 1.1.7) it is mitigated mainly by trusted, digest-pinned images, and LAN-only exposure is recommended.
- Vendor GUI project actions (Container Manager on DSM) are never used on Ingat projects (operator rule); `status` reports `changed-outside`.
- Recovery relies on Ingat bundles plus an off-host copy and never on snapshots (on DSM, Snapshot Replication exists only on Btrfs volumes). Ingat does not depend on the storage driver; the aufs driver used on DSM ext4 volumes survives only in Synology's build (removed upstream in Engine 24.0), so a storage-driver change is treated as a new build (risk R14, [ARCHITECTURE.md](../ARCHITECTURE.md) §12).
- New spike S15: the apps' images on a DSM 4.4 kernel.

## Alternatives

A Synology-only product with a VPS path later (the earlier text of this ADR; rejected after the owner's clarification: it framed a general tool around one appliance, and generic Linux hosts, which CI already reproduces, would have waited for M4). Branch on the platform name to pick behaviour or defaults (rejected: the generality rule; a new appliance would need a core change). Require a host certification only on vendor builds (rejected: no detected fact that separates a vendor build from an upstream one is verified yet, and one uniform rule is simpler; a local `selftest --host` per platform build takes minutes). An `amd64`-only image with arm64 behind a trigger (the earlier text; rejected: arm64 servers, VPS and boards are in scope, and GitHub-hosted arm64 runners cost nothing for a public repository). Leave logging to the daemon default (rejected: `ingat logs` and log snapshots would depend on a vendor driver, and logs would neither rotate predictably nor leave with `--rm`). Support DSM 7.1 hosts with the legacy Docker package through a legacy API tier (rejected: Engine 20.10 is out of support and below the API floor, and DSM 7.1 is out of extended life with no further fixes expected).

## Consequences

[ARCHITECTURE.md](../ARCHITECTURE.md) §11 holds the support tiers, the platform traits and how Ingat handles them, the first platform profile and the minimum host requirements; §3.4 holds the generic install and the DSM profile's install values. S11 shrinks to the `cpus: "0"` and memory-limit checks; S3 checks `flock` on the first host's local volume (a volume with another filesystem is covered by its own host certification); S13 also confirms the arm64 runner; owner decision OD-11's architecture condition does not fire for the first host. A certification file names only the platform software and architecture (OS or appliance release and build such as the DSM build, the Engine package build such as the Container Manager build, the Engine version, Git commit and build time, containerd and runc versions, kernel, `x86_64` or `aarch64`), never a device model, hostname, address, instance path or details of the unit. Every platform update needs a re-certification by `selftest --host`, and scheduled drills refuse until it passes ([ADR-0014](0014-tiered-version-gate.md)). The systemd and cron renderers move from M4 slice 12 to M3 slice 8 (about 50 lines; totals unchanged), and M4 slice 12 becomes the generic Linux host certification (VPS or server) ([ROADMAP.md](../ROADMAP.md)).
