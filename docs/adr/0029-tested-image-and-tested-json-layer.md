# ADR-0029 One image build per pipeline, tested by every lane, with tested.json as its final layer

**Status:** Accepted (2026-10-15).

## Context

CLAUDE.md (Testing and Validation) and [ARCHITECTURE.md](../ARCHITECTURE.md) §10.1 require each lane to test "the exact tool image built in that pipeline", and §3.6 requires every release to embed `tested.json`, generated by CI from the lanes that passed. The two requirements meet in a cycle: `tested.json` is known only after the lanes ran, and embedding it changes the image. Building the image separately in each lane, and again for the release, does not give the exact artifact either: Debian packages installed at build time can differ between builds minutes apart.

## Decision

- One job per pipeline builds the multi-arch image once (`linux/amd64`, `linux/arm64`) from `image/versions.lock` and exports one `docker save` tarball per architecture as a pipeline artifact. Every lane loads the tarball of its own architecture into its scratch daemon and tests exactly those layers.
- A lane's test image adds one final layer to it: `tested.json` listing the lane's own Engine line, architecture, CLI and Compose, so the gate tier 2 suites can run. The release image is the same build plus one final layer holding the `tested.json` generated from the lanes that passed. All other layers, and therefore all code, are byte-identical to what the lanes tested; the release notes name both digests.
- `tested.json` is read only from the image's package data; there is still no file or flag on a host that widens gate tier 2 (ADR-0014).

## Alternatives

Build per lane and again for the release (rejected: not the exact artifact). Embed a `tested.json` written before the lanes run (rejected: it would claim combinations no lane has passed). Ship `tested.json` beside the image as a release asset installed on the host (rejected: a host file that widens gate tier 2 is forbidden by ADR-0014).

## Consequences

The CI workflow gains a build job that the lanes depend on, and the release workflow reuses the pipeline's build instead of rebuilding. A lane's verdict covers the tested layers; the final `tested.json` layer is data the gate reads, covered by the gate's own unit tests.
