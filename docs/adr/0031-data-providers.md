# ADR-0031 Data providers: tool-shipped, digest-pinned provider images declared per data set

**Status:** Accepted (owner, 2026-10-19). Supersedes [ADR-0010](0010-one-data-strategy-app-native-tasks.md) (one data strategy): a second strategy, `provider`, joins `tasks`. Narrows the deferred `cold` strategy of [ROADMAP.md](../ROADMAP.md) §4 to raw copies of an engine's own data directory. Changes no entry of the never-list in [ARCHITECTURE.md](../ARCHITECTURE.md) §1.4 except its wording for engine code: `src/` still holds none and names no engine; provider images under `providers/` carry the engine code, and `image/providers.lock` is the only place that names a kind.

## Context

The onboarding checklist ([ARCHITECTURE.md](../ARCHITECTURE.md) §11.3 item 2) requires an app to ship `backup`, `restore`, `verify` and a schema read in its own image with an exit-code contract. Third-party images (password managers, wikis, feed readers, photo and document stores) ship none, so Ingat cannot manage them, and a one-container manifest costs about 255 lines (`fixtures/fx-lite/ingat.toml`). The owner requires a view for newcomers, coverage of many third-party apps and a free and a paid tier; those need a declarative surface that a form can generate and a certification artifact that ships with the tool. The M1 operator loop was exercised end to end on a scratch daemon during development ([README](../../README.md) Status); nothing has run in CI or on a host yet.

Two alternatives were designed and judged against this one: a raw `cold` copy plus a manifest generator, and recipes in a separate catalog that name helper images of their own. Both reject the same thing this ADR rejects (engine code in `src/`); they differ in who pins and tests the helper and in how much the core changes.

## Decision

1. **Two data strategies on one step model:** `tasks` (unchanged) and `provider`. `cold` stays deferred; its trigger narrows to raw copies of an engine's own data directory.
2. **Manifest** (a new [MANIFEST_SPEC.md](../MANIFEST_SPEC.md) §2.8, present as a Planned stub from this ADR and filled when slice P1 lands; the keys are additive in schema 1 before the M2 freeze, else the first schema-2 change): `[data.<name>]` with `provider` (a kind that `image/providers.lock` lists; today `postgres`, `mysql`, `mariadb`, `sqlite`, `files`), `major`, `service` (role `data`), `store`, `database`, `user`, `password = { secret = "<name>" }`, `port`, `databases` (sqlite), `exclude` (files), `ready`, `timeout`; `[stores.<name>] backup = false` for cache stores (never captured, recreated empty). `[backup] strategy = "provider"` is implied by the presence of `[data.<name>]` when the manifest declares no `[backup]`; an explicit `[backup]` may name it for the mixed mode of P2. `[schema]` stays optional: without it every writer or data-service image change is data-changing (F6 held conservatively).
3. **The lock is the only catalogue of kinds and traits.** `image/providers.lock` holds one entry per `(kind, major)`: `{image: "self" | {amd64: <digest>, arm64: <digest>}, contract, verbs, ready_argv, port, network: "none" | "data-service", run_as: "store-owner" | "root", keep_caps: [...], keys: {required: [...], optional: [...]}}`; `keys` names the `[data.<name>]` keys the kind takes, and `validate` checks each data set against its entry's `keys`. Provider images are tool artifacts: built from `providers/<kind>/{Dockerfile,entrypoint.sh}` in the release pipeline, both architectures, with SBOM and digests in `SHA256SUMS`, and copied into the tool image as a final layer beside `tested.json` ([ADR-0029](0029-tested-image-and-tested-json-layer.md)). `files` is the tool image itself (`image: "self"`; GNU tar present), so four images, not five. `validate` accepts a `provider` value only when the lock lists it, and `src/ingat/model/providers.py` expands from the entry's fields only: no code in `src/` names a kind, the forbidden-literal lint stays as it is, and the only literal in `src/` is the lock's own schema. No manifest, instance or host key may name a provider image, and a provider bump is a tool release.
4. **Contract v1**, the public interface a provider image must satisfy, documented in `docs/PROVIDER_CONTRACT.md` (a P0 deliverable, with a reference image and a conformance kit so that anyone can build and self-check a provider; a contributed provider is reviewed by the owner and pinned in a tool release). The minimum fixed here: the entrypoint is `/usr/local/bin/ingat-provider <verb>`; verbs `ready` (read, scratch; exit 0 ready, 2 not ready yet, 1 unreachable), `backup` (read; `/out` = the stage, writable; writes `data/<name>/` plus `provider.json`), `verify` (read; `/in` = the private bundle copy, read-only; no server), `restore` (data; isolated projects only; `/in` read-only, `/data` = an empty generation, writable; refuses a non-empty target), `check` (read; counts and integrity against `provider.json`). Exit map 0 ok, 1 failed, 2 refused, 3 finding. The container runs as the task `user` of the expansion: an entry with `run_as = "store-owner"` (today `files`) runs as the store's owner `uid:gid`, which the expander reads from the generation; an entry with `run_as = "root"` runs as root with only its `keep_caps`. Inputs: `INGAT_PROVIDER_NAME`, `INGAT_PROVIDER_KIND`, `INGAT_PROVIDER_MAJOR`, `INGAT_PROVIDER_HOST`, `INGAT_PROVIDER_PORT`, `INGAT_PROVIDER_DATABASE`, `INGAT_PROVIDER_USER`, `INGAT_PROVIDER_PASSWORD_FILE` (a Compose secret file; never argv), `INGAT_PROVIDER_TIMEOUT_SECONDS`; argv carries the verb only. `provider.json`: `contract`, `kind`, `major`, `engine_version`, `created_at`, `objects: [{name, count, sha256}]`. SIGTERM means stop within the grace period and exit 1. Stdout is plain text, at most 64 KiB, bounded and redacted by the runner; payload bytes go to the mounts only.
5. **Expansion** (`src/ingat/model/providers.py`, pure): each `[data.<name>]` becomes one override-only service `ingat-data-<name>` (the lock digest, `pull_policy: never`, Compose profile `ingat-data`, the data service's networks or none per the entry's `network`, the password secret, `read_only`, `no-new-privileges`, `pids_limit`, `mem_limit`, `logging: none`, and `cap_drop` of every capability except the entry's `keep_caps`, never `cap_add`; an entry with `run_as = "store-owner"` has an empty keep set), tasks `data.<name>.ready|backup|verify|restore|check` (`mode = "run"`, `operator = false`, `image = "bundle"` for verify, restore and check), a probe `data.<name>.ready` (`exec` into the data service with the entry's `ready_argv`, the store's readiness probe unless the manifest sets one), and `[backup]`, `[restore]` and `[drill]` tables when the manifest declares none. Planners, step types, the orphan rule, the journal, the crash matrix and the approval classes see ordinary tasks. The synthesized `ingat-data-<name>` service is an ordinary image service pinned by digest, never a Compose `provider:` service, which the policy keeps refusing. The policy gains one rule: `reserved-service` for an app-declared `ingat-data-*` service. The clean-stop evidence (below) is captured by a helper beside `ops/steps_build.py`, not in `core/steps.py`, which is near the 600-line cap.
6. **Records.** `bundle.json` stays bundle format 1 and gains only the optional keys `providers{}` and `stop{service: {exit, clean}}`. The consistency value `online-provider` arrives in two steps, so that `bin/ingat.prev` keeps reading what the new version writes ([ADR-0023](0023-record-compatibility-within-state-schema.md)): the release before P1 teaches every reader to treat an unknown `consistency` as "copied in a way this version does not know" while the hash and level logic stay unchanged, with an upgrade-suite case (the previous version lists, verifies and prunes a bundle that carries the new value); P2 then writes it (P1 writes only `writers-stopped` bundles). A pre-change or final capture whose writers did not stop cleanly fails its capture step with code `unclean-stop`: the undo restarts the writers, the operation ends `failed-unchanged` (exit 3) with `next` naming the data service to inspect, and nothing is replaced (F6). A scheduled capture that stopped writers unclean still seals the copy and raises the attention `unclean-backup`, so a nightly backup never fails silently. `prepare` pulls the lock digests; the image ledger keeps them (F11).
7. **Catalog:** a public repository (`lisahq/ingat-catalog`, Apache-2.0), `apps/<app>/{compose.yaml,ingat.toml,README.md,README.vi.md,catalog.toml,tested.json}`, tags `<app>/<upstream>-<n>`, consumed through the existing `[source]` keys. Entry states `draft` and `certified` ("certified" = the lifecycle loop passed on the tested Engine lines; a red nightly freezes the entry at its last passing tag). A scheduled job opens digest-bump pull requests; CI runs `validate`, the lifecycle loop on both dind tags and an update from the previous tag; `catalog.json` is a release asset. Community entries are accepted with a named maintainer and a passing nightly. The tool never discovers releases.
8. **Plain words:** every user-visible text of providers, pause texts, restore notices, catalog READMEs and the consistency vocabulary (`writers-stopped` = "copied while the app was paused", `online-provider` = "copied while the app was running") follows the plain-language rule and passes a lint in CI, in English and Vietnamese.

**Owner decisions recorded (2026-10-19).** Schedule: the contract, the first two images and their CI lane (P0) run parallel to M2; the core change (P1) lands right after the M2 exit gate with `[data]` additive in schema 1; the remaining providers and catalog entries (P2) follow. Providers: `postgres` and `files` first, then `sqlite`, `mariadb`, `mysql`; no `mongo`. Providers live in this repository; a bump is a tool release. Catalog as above; the first ten apps include large-media apps with their copy limits stated, and a home-automation app only as `draft`. `backup = false` for cache stores. No `[schema]` means every writer image change takes a pre-change bundle. Readiness comes from the lock's `ready_argv`; no new probe kind. `files` copies whole stores; the limit is stated per entry. No `catalog list` command in v1.

## Alternatives

- **`cold` strategy plus a manifest generator (`wrap`)**: rejected. It mounts real secrets into drills, has no online form (every nightly backup is gate tier 2, so a platform update stops all backups until re-certification), raw copies lock the engine major forever, `verified` means hash only, and the generator costs about 700 core lines for what a lint script or the web view can do.
- **Recipes in a separate catalog that name their own helper images**: rejected as the first form, kept as the closest alternative. Zero core lines, but three repositories and pipelines, a second recipe language, helpers that the tool neither pins nor tests, ~120-line manifests, and a quality that varies per recipe. Its counts check, online SQLite, plain-words lint, build order and `draft`/`certified` states are adopted here.
- **Engine code inside the core**: rejected; the reasoning of ADR-0010 stands.

## Consequences

Floors preserved: F2/F9 (`validate` reads the lock offline); F4/F11 (the digest is frozen in the plan and run through `image = "bundle"`); F5/F15 (every verb is a `RunTask` with per-attempt names and op labels; `restore` runs only in an isolated project into a new generation); F6 (writers stopped, clean-stop evidence); F7 (the provider refuses a non-empty target, a second guard); F8 (provider containers are owned; adoption stays payload-based, and the runbook prints the hand-run provider line for a foreign deployment); F10 (`verified` = hash plus every synthesized verify `ok`); F12 (the secret reaches the provider only as a Compose secret file; a canary case is added); F13 (project networks only; none for entries with `network = "none"`, today `files` and `sqlite`; no ports); F16 (the store's `exec` probe plus the client-side `ready` before every verb). Forbidden: any image not in the lock; a long-lived provider; the socket, `cap_add`, host networking or binds outside generations, the stage and the bundle copy; `files` over an engine's own volume; a restore into a non-empty or live target; executing anything from a bundle; a user- or catalog-supplied script in place of a verb; auto-picking a catalog tag.

Required suites for P1 (CLAUDE.md, Testing and Validation), on a provider fixture `fx-prov` (a third-party image plus `[data]`): no-trace; the crash matrix regenerated, because the synthesized `data.<name>.*` tasks add steps to the deploy, backup, verify and restore plans, with the `unclean-stop` case; session loss; secret canary (the password file never in argv, records, bundles or logs); readiness (`data.<name>.ready` before every verb); isolation (a provider restore only in an isolated project); recreate scope (adding or removing `[data]` leaves every live container ID unchanged, because the provider service lives in a profile); generation safety (a restore refuses a non-empty target; the previous generation stays intact); upgrade (the previous version reads a bundle the new one wrote). The provider CI lane (P0) runs the conformance kit per kind on both dind tags and arm64.

Costs: about 500 core lines (every module under 600; the stop-evidence helper lives beside `ops/steps_build.py`), about 700 lines of shell and Dockerfiles, about 900 test lines, docs in two languages, and roughly half a day a week of digest-bump review; a provider major bump is about a day including the tool release; each base-image CVE implies a tool release. A third-party app's manifest shrinks to 46-70 lines. Apps that need host networking or devices stay policy refusals, recorded as generality gaps. Week estimates in [ROADMAP.md](../ROADMAP.md) §5.
